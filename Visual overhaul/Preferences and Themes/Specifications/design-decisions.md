# Preferences and Themes — Settings Studio

Use a **Settings Studio** surface with a short section navigator and readable settings groups. The alternative Compact Preferences uses a horizontal section selector and a narrow stacked body. Keep settings in one store and renderer, shared by both presentations. Start with actual app settings; illustrative switches are not authorization to invent features.

Appearance covers available themes and supported motion / density controls. Workspace covers persisted panel geometry, navigator layout and session preferences if implemented. Document-specific export defaults and security / permission properties belong in their appropriate document workflows, not a confusing global toggle. Preserve all existing preferences, theme choices and shortcut editing access through a source inventory. Do not remove an existing theme because the preview shows Light / Dark / System.

Use 720–880 logical px preferred width, a 160–180 px section navigator, 24 px body padding and 20 px group gaps. At constrained widths stack the section selector above the body. A setting row contains a clear label, native control, concise explanation when necessary, actual current value and validation only if relevant. Avoid a boxed card per toggle. Controls use the shared 9 px radius, 13–14 px text and 36–40 px minimum height; coarse targets are 44 px.

Theme choice should include System only when the application can reliably observe and persist it. Apply light / dark semantic tokens to surfaces and controls; keep the actual PDF page content unchanged. Keep full saturated document-tab identities, with contrasting selected text, under every theme. Operating-system high contrast / forced colors overrides ornamental fills while retaining filenames, states and visible focus. Provide a truthful fallback for unsupported translucent materials; avoid glass beneath dense settings text.

Home decorative motion follows the intersection of user preference, OS reduced motion, visibility and power policy. An enabled preference must never override OS reduced motion. Preserve the paused state between visits. Do not animate the brand logo or document pixels. Tool label visibility applies only to components with an accessible compact alternative; recommended siderail workspace labels remain visible.

Choose and document either immediate application or Apply / Cancel per setting group. Do not mix silently. For immediate reversible settings, restore the prior value if persistence fails and show an actionable error. For Apply / Cancel, keep a draft separate from committed settings, validate before apply and discard draft on Cancel. Restore defaults states its scope and restores settings rather than deleting documents, history or user assets. Sensitive preferences must retain existing explicit security controls; visual styling does not weaken them.

Acceptance: all original setting entry points, persistence / failure rollback, app restart, System appearance changes, OS reduced motion, short / narrow windows, display scaling, keyboard / screen-reader labels, all supported themes and tab-color readability. Reference controls change the local preview only, not real app preferences.

## Shared visual and implementation rules

This category extends Quiet Precision. Surface / canvas: #FFFFFF / #F5F6F8 in light, #20232B / #171A21 in dark. Main text: #485164 / #B8C0D0; strong: #232A38 / #EEF1F7; small supporting text: #667085 / #929BAC. Boundary: #E1E4EB / #3B414E; interactive violet: #7050D6 / #B9A4FF; selected surface: #F0EBFC / #302740. Read the unified semantic tokens and the Consistency Corrections folder. Document-tab identities remain colorful and stable per session, confined to the rail.

Use a 4 px spacing grid, 9 px control radius, 12–14 px floating surface radius, 16–24 px content spacing and 140 ms emphasis transitions. Attached panels use hairline boundaries, not floating shadows. UI typography follows the existing Typography folder. Original icons follow the 24-unit / 1.65 round-stroke grammar; this reference uses host Lucide icons for illustration. Never replace PDF fonts or pixels with UI tokens. Reduce motion and high contrast apply across the category.

First audit all relevant entry points, existing handlers, source data, capability predicates, settings / document stores, state transitions and any engine constraints. Reuse command / menu / dialog / form primitives; do not introduce parallel stores or CSS overrides at each call site. Only render information the app can support truthfully. This handoff designs behavior for capabilities to verify, not evidence that every pictured feature already exists.

Implementation phases: inventory and state contracts; shared primitives / tokens; category migration across every entry point; asynchronous and cross-document correctness; accessibility / performance; real app regressions and visual review. Preserve document content, session identity, undo history, keyboard bindings, permission checks, save / close / cancellation policies and native Windows chrome. Test all supported themes, long and localized labels, restored / maximized windows, 200% scaling, keyboard and relevant error / empty states.

## Reference limits

Both visual alternatives are local interaction prototypes. Filenames, people, comments, form labels, matches, progress, output geometry and command results are illustrative unless specifically documented as installed-app observations. They do not run OCR, PDF editing, conversion, save, print, mail, collaboration or system preference changes. The prototype's short fixture arrays and state handlers are not production data models. Example scenario controls such as Continue / Show failure on the Activity reference exist solely to inspect state styles and must not become product commands. Native dialogs, screen-reader tree semantics, forced colors, drag transforms, focus trapping and engine integrations must be implemented and tested with the real application.
