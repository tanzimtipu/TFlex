# Selection and Manipulation — Inspector First

Create one selection controller for native text objects, images, annotations, crop regions and supported form fields. Their semantics differ; share visual geometry and event plumbing while preserving separate engine operations. **Inspector First** puts detailed properties in the existing inspector and only essential Apply / Cancel controls near the object. The alternative Context Bar exposes a small anchored quick-format row with the same inspector available for advanced properties.

Selection uses a 1 px violet boundary and 6–8 px visual handles in screen coordinates, with larger invisible hit targets (approximately 24 px fine pointer / 44 px coarse pointer where non-overlapping). Current focus, hover, selected geometry and in-progress draft are separate states. Multiple objects show a common bounding region only when the engine supports transforming them together. Avoid a full-width glow or opaque fill that conceals text. No red Delete button immediately beside Apply as the default highest-salience choice; keep Delete in a separated More action using established policy.

Context controls must be anchored to the visible selection's screen rectangle, transformed using crop, rotation, zoom, viewport scroll and spread layout. Prefer below the selection, flip above near the footer, and clamp horizontally within the document viewport. Avoid covering the selected text, rail, inspector, dock or viewing controls. If the object is too small / occluded, place the editor in the inspector rather than rendering overlapping toolbars. Keep a single comment entry surface, not a separate control bar and duplicate comments card both covering the page.

Draft edits update an intentional preview transaction. Apply commits exactly one supported undo unit; Cancel restores the original object and clears the draft. If the existing engine uses immediate edits / undo instead, preserve that model and label controls accordingly—do not fake transaction semantics by changing DOM text. Handle document switching and tool switching deliberately: retain draft, confirm discard, or commit using existing policy, never silent loss. Selection alone never marks the PDF dirty.

Resize, rotate and drag need device-independent transforms and capture / cancellation handling. Preserve aspect ratio according to the real modifier / control policy, honor page boundaries where required, expose numeric / keyboard alternatives, and escape cleanly if pointer capture is lost. Snapping appears only where supported; a visual guide is not proof that the object will land correctly. Protect engine coordinate precision and avoid rounding PDF geometry to screen pixels.

Text editing preserves PDF font embedding / substitution rules, baseline, original content semantics and unsupported-content explanations. UI typography must not become a document font. Property changes respect permissions, signed-document state, annotation vs content differences and existing warnings. Never advertise editable text merely because the renderer exposes a text layer.

Acceptance: rotated / cropped / mixed-size pages, zoom extremes, spreads, scroll, selection at every viewport edge, tiny / large objects, multiple selections, pointer capture loss, keyboard controls, Apply / Cancel / undo, native font issues, unsupported text, permissions and tab switch. The reference changes local example text only; it is not a PDF editing engine or a working resize model.

## Shared visual and implementation rules

This category extends Quiet Precision. Surface / canvas: #FFFFFF / #F5F6F8 in light, #20232B / #171A21 in dark. Main text: #485164 / #B8C0D0; strong: #232A38 / #EEF1F7; small supporting text: #667085 / #929BAC. Boundary: #E1E4EB / #3B414E; interactive violet: #7050D6 / #B9A4FF; selected surface: #F0EBFC / #302740. Read the unified semantic tokens and the Consistency Corrections folder. Document-tab identities remain colorful and stable per session, confined to the rail.

Use a 4 px spacing grid, 9 px control radius, 12–14 px floating surface radius, 16–24 px content spacing and 140 ms emphasis transitions. Attached panels use hairline boundaries, not floating shadows. UI typography follows the existing Typography folder. Original icons follow the 24-unit / 1.65 round-stroke grammar; this reference uses host Lucide icons for illustration. Never replace PDF fonts or pixels with UI tokens. Reduce motion and high contrast apply across the category.

First audit all relevant entry points, existing handlers, source data, capability predicates, settings / document stores, state transitions and any engine constraints. Reuse command / menu / dialog / form primitives; do not introduce parallel stores or CSS overrides at each call site. Only render information the app can support truthfully. This handoff designs behavior for capabilities to verify, not evidence that every pictured feature already exists.

Implementation phases: inventory and state contracts; shared primitives / tokens; category migration across every entry point; asynchronous and cross-document correctness; accessibility / performance; real app regressions and visual review. Preserve document content, session identity, undo history, keyboard bindings, permission checks, save / close / cancellation policies and native Windows chrome. Test all supported themes, long and localized labels, restored / maximized windows, 200% scaling, keyboard and relevant error / empty states.

## Reference limits

Both visual alternatives are local interaction prototypes. Filenames, people, comments, form labels, matches, progress, output geometry and command results are illustrative unless specifically documented as installed-app observations. They do not run OCR, PDF editing, conversion, save, print, mail, collaboration or system preference changes. The prototype's short fixture arrays and state handlers are not production data models. Example scenario controls such as Continue / Show failure on the Activity reference exist solely to inspect state styles and must not become product commands. Native dialogs, screen-reader tree semantics, forced colors, drag transforms, focus trapping and engine integrations must be implemented and tested with the real application.
