# Print and Output — Output Studio

Use **Output Studio** as a clear bridge from document to output: source / page scope, settings and truthful preview, with the primary action describing the actual operation. The Compact Output alternative places settings above a small preview for constrained windows. Printing and exporting remain distinct handlers even when they share layout primitives.

Reuse the existing Windows print flow, printer capabilities, PDF render / export engine and document permissions. Keep Print available from its actual command and shortcut, not only the Deliver workspace. Do not replace the native print dialog with a cosmetic local simulation if native printer selection and driver options are required. An app-level preview may precede the native flow when supported; label the action “Continue to print” when it opens another dialog rather than immediately printing.

Settings include only supported destination, page range, copies, orientation, scaling and other real engine / driver options. The reference's controls are illustrative. Page range validation uses the shared range parser and real count. Distinguish physical page positions from PDF page labels. Respect exact user order / duplicate-page semantics as established by the app; do not reuse an extraction parser that silently removes duplicates if printing supports them. Unknown counts stay unknown, and errors remain associated with their fields.

The preview renders actual output geometry, including media / crop size, fit / actual-size policy, orientation, printable area and annotations / forms where supported. Preserve document fonts, images, transparency, vector content and background colors according to the engine. Never use a UI-scaled canvas screenshot as final printed content. If margins, duplex, color or printer-dependent capabilities are unknown until the native dialog, make that boundary clear. Do not invent “100% fidelity” badges or estimated file sizes.

Use 16 px title, 13–14 px setting values, 12 px destination / scope metadata, 24 px content spacing and the shared controls. White paper remains white against either theme. Center the preview in a neutral stage without tinting actual output pixels. Before execution, summarize meaningful consequences: selected pages, actual destination and output format. Do not expose internal implementation details unless needed to choose a meaningful output option.

Cancellation keeps the source document open and intact. Failure retains settings and provides a supported retry / choose-destination path. Completion means a real output has been persisted or a print job accepted at the supported boundary, not merely that rendering began. Do not claim physical printing finished when only spool submission is known. Export saves through the established atomic / safe storage flow and preserves overwrite prompts. User-facing formats derive from actual converters; unsupported formats do not appear enabled.

Acceptance: all / selected / invalid ranges, page labels, copies, rotated / cropped / mixed media pages, annotations / interactive forms, actual size / fit policies, print cancellation, destination failure, engine render failure, native dialog availability, export / overwrite handling, permissions, keyboard and high contrast. Validate generated files and print-render geometry with real fixtures. The reference never prints, exports or writes a PDF.

## Shared visual and implementation rules

This category extends Quiet Precision. Surface / canvas: #FFFFFF / #F5F6F8 in light, #20232B / #171A21 in dark. Main text: #485164 / #B8C0D0; strong: #232A38 / #EEF1F7; small supporting text: #667085 / #929BAC. Boundary: #E1E4EB / #3B414E; interactive violet: #7050D6 / #B9A4FF; selected surface: #F0EBFC / #302740. Read the unified semantic tokens and the Consistency Corrections folder. Document-tab identities remain colorful and stable per session, confined to the rail.

Use a 4 px spacing grid, 9 px control radius, 12–14 px floating surface radius, 16–24 px content spacing and 140 ms emphasis transitions. Attached panels use hairline boundaries, not floating shadows. UI typography follows the existing Typography folder. Original icons follow the 24-unit / 1.65 round-stroke grammar; this reference uses host Lucide icons for illustration. Never replace PDF fonts or pixels with UI tokens. Reduce motion and high contrast apply across the category.

First audit all relevant entry points, existing handlers, source data, capability predicates, settings / document stores, state transitions and any engine constraints. Reuse command / menu / dialog / form primitives; do not introduce parallel stores or CSS overrides at each call site. Only render information the app can support truthfully. This handoff designs behavior for capabilities to verify, not evidence that every pictured feature already exists.

Implementation phases: inventory and state contracts; shared primitives / tokens; category migration across every entry point; asynchronous and cross-document correctness; accessibility / performance; real app regressions and visual review. Preserve document content, session identity, undo history, keyboard bindings, permission checks, save / close / cancellation policies and native Windows chrome. Test all supported themes, long and localized labels, restored / maximized windows, 200% scaling, keyboard and relevant error / empty states.

## Reference limits

Both visual alternatives are local interaction prototypes. Filenames, people, comments, form labels, matches, progress, output geometry and command results are illustrative unless specifically documented as installed-app observations. They do not run OCR, PDF editing, conversion, save, print, mail, collaboration or system preference changes. The prototype's short fixture arrays and state handlers are not production data models. Example scenario controls such as Continue / Show failure on the Activity reference exist solely to inspect state styles and must not become product commands. Native dialogs, screen-reader tree semantics, forced colors, drag transforms, focus trapping and engine integrations must be implemented and tested with the real application.
