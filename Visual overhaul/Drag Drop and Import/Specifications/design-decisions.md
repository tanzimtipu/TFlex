# Drag Drop and Import — Intake Tray

Use **Intake Tray** as a deliberate file intake surface, shared by Home, Open, canvas drops and From images where their behaviors overlap. The Compact Intake alternative uses a small destination banner and a concise queue instead of a large central drop target. Reuse real open / import / conversion capabilities; do not create a converter by accepting a file extension in a visual prototype.

Show a subtle canvas / Home drop indication only while an eligible drag enters the application. Highlight the destination explicitly: open new documents, insert pages into the current document, or build a PDF from images. When more than one operation is plausible, ask through the intake surface with meaningful choices. Never infer destructive replacement from the pointer's location alone. Dropping must not unexpectedly mutate the active PDF before intent is clear.

The intake list shows basename, detected supported type, state and Remove from queue. Removal is not file deletion. Use safe text nodes for names, allow wrapping / disambiguation, and keep full locations in accessible details rather than exposing giant paths in rows. Preserve user order for image-to-PDF creation and provide actual drag / keyboard reorder if supported. Do not silently alphabetize or duplicate entries unless that is the existing documented behavior.

Actions depend on actual content / engine detection and permission, not extensions alone. PDF files may open as separate sessions; image collections may create a single PDF through the existing image-creation pipeline. Mixed or unsupported inputs have explicit item errors and supported choices; no bogus “Ready” on unknown files. Empty, validating, ready, converting, failed / partial and completed states use the Feedback handoff. Keep successful inputs and failed inputs visible through partial failures.

Suggested drop target: 12 px corner radius, a single quiet dashed boundary, a 28 px folder glyph, short title and visible Choose files control. Never require drag-and-drop: a labeled native file picker and supported clipboard flow remain accessible. File inputs are local and require explicit user interaction; the prototype reads filenames only and does not upload or parse selected contents. Production must use supported file references and avoid arbitrary path evaluation or embedded content execution during previews.

Image creation settings use actual preview thumbnails, order, page size / margins / orientation if supported, and quality controls from the existing operation. Show precise consequences for recompression only when known. Clipboard input must explain a missing / unsupported clipboard rather than creating an empty PDF. Final output/session creation follows existing save, naming and dirty-state semantics; a new in-memory document is not automatically saved.

Acceptance: picker and drop equivalence, one / many PDFs, images, mixed / unsupported / misleading extensions, unreadable / protected files, duplicate basenames, ordering, cancelled conversion, partial errors, clipboard failure, empty input, 200% scaling and keyboard alternatives. Do not test import against private files merely to obtain attractive thumbnails; use purpose-built fixtures.

## Shared visual and implementation rules

This category extends Quiet Precision. Surface / canvas: #FFFFFF / #F5F6F8 in light, #20232B / #171A21 in dark. Main text: #485164 / #B8C0D0; strong: #232A38 / #EEF1F7; small supporting text: #667085 / #929BAC. Boundary: #E1E4EB / #3B414E; interactive violet: #7050D6 / #B9A4FF; selected surface: #F0EBFC / #302740. Read the unified semantic tokens and the Consistency Corrections folder. Document-tab identities remain colorful and stable per session, confined to the rail.

Use a 4 px spacing grid, 9 px control radius, 12–14 px floating surface radius, 16–24 px content spacing and 140 ms emphasis transitions. Attached panels use hairline boundaries, not floating shadows. UI typography follows the existing Typography folder. Original icons follow the 24-unit / 1.65 round-stroke grammar; this reference uses host Lucide icons for illustration. Never replace PDF fonts or pixels with UI tokens. Reduce motion and high contrast apply across the category.

First audit all relevant entry points, existing handlers, source data, capability predicates, settings / document stores, state transitions and any engine constraints. Reuse command / menu / dialog / form primitives; do not introduce parallel stores or CSS overrides at each call site. Only render information the app can support truthfully. This handoff designs behavior for capabilities to verify, not evidence that every pictured feature already exists.

Implementation phases: inventory and state contracts; shared primitives / tokens; category migration across every entry point; asynchronous and cross-document correctness; accessibility / performance; real app regressions and visual review. Preserve document content, session identity, undo history, keyboard bindings, permission checks, save / close / cancellation policies and native Windows chrome. Test all supported themes, long and localized labels, restored / maximized windows, 200% scaling, keyboard and relevant error / empty states.

## Reference limits

Both visual alternatives are local interaction prototypes. Filenames, people, comments, form labels, matches, progress, output geometry and command results are illustrative unless specifically documented as installed-app observations. They do not run OCR, PDF editing, conversion, save, print, mail, collaboration or system preference changes. The prototype's short fixture arrays and state handlers are not production data models. Example scenario controls such as Continue / Show failure on the Activity reference exist solely to inspect state styles and must not become product commands. Native dialogs, screen-reader tree semantics, forced colors, drag transforms, focus trapping and engine integrations must be implemented and tested with the real application.
