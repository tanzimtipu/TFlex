# Jovrel interaction surfaces: Task Surfaces

Proposed visual system for every in-app dialog, toolbox, popover and menu, including surfaces absent from the screenshots. Extend Quiet Precision and the user-requested colorful tab revision. Tab identity colors belong to document tabs; task surfaces use neutrals and the shared violet action/selection accent. This is a visual and behavioral handoff, not an implementation in TFlex.

## Diagnosis and direction

The File menu is tall and translucent enough to compete with the underlying page. Its section headings, command labels and boxed shortcuts add visual noise. The Create PDF from images dialog is substantially taller than its empty content needs. The Stamp dialog clips introductory content beneath its header and allocates much of the body to large option rows and an oversized preview. Object actions and comments appear as stacked disconnected floating surfaces, with inconsistent action order. The extract dialog provides useful range/result information and is a good functional starting point.

Use one family of opaque, softly rounded task surfaces with crisp text, 1px structural borders and restrained elevation. Distinguish the surface type by interaction purpose, not by unrelated colors. A dialog contains a complete transaction; a toolbox supports a selected object; a menu dispatches commands; a popover adjusts one property. A hover tooltip only describes a control. These share tokens while retaining distinct keyboard, focus, dismissal and commit behavior.

## Visual anatomy and dimensions

Dialog: 16px corner radius; 1px border; proposed elevation 0 12px 36px with light #232A381A/dark #00000040. Header: title plus one line of actual document/task context and a 32px close target. Body: concise labeled fields, previews and relevant helper text. Footer: one primary verb, Cancel, and optional meaningful status. Use 24px padding and 16px field-group spacing on normal desktop layouts. Header and footer remain visible when a body needs scrolling; the body must start below the header, with no content hidden beneath either region.

Content-driven width classes: compact 400–440px, standard 520–560px, preview/list 640–720px. Logical dimensions are proposals, not screenshot measurements. Use actual available window bounds and 16–24px viewport margins; keep width below viewport minus margins and total height below viewport minus margins. Grow image lists after input arrives; don't reserve a giant blank canvas. For short forms, fit height to content. For long forms, use a single bounded body scroll region with preserved header/footer, not several nested scrollbars. At constrained widths, stack field groups and collapse preview columns; don't shrink type. Native file dialogs and Windows system prompts remain native.

Menu/popover: 12px radius, 1px border, 6px menu padding, 36px row height, typical 260–320px width, restrained shadow 0 8px 24px. Solid surface guarantees legibility independent of the page underneath. Reserve aligned slots for optional icon, label, checked state, verified shortcut and submenu chevron. Avoid a colored icon on every row. Shortcuts appear as quiet aligned text rather than heavy keycap boxes. Separate related groups with a small gap/divider; avoid repeated uppercase headings in compact menus. Preserve clear headings where they aid navigation in large menus. Clamp menu height to available space, flip placement near edges and scroll only its list when necessary. Never silently clip bottom commands.

Toolbox: 12px radius, 8px padding, 32px targets (44px coarse pointer), typically 280–420px wide and sized to contents. One coherent action row, optionally one expanded property/comment region. Place close to selection with an 8–12px offset while avoiding the object handles, text insertion area, dock and zoom controls. Compute collision-aware placement using viewport and transformed object bounds; flip above/below and clamp at edges. Avoid a chain of several floating boxes. Detailed typography/geometry lives in the existing inspector; quick actions stay in the toolbox and call the same handlers. During drag/resize, keep selection handles usable and avoid a jumping popup; use the framework's existing behavior.

Shared typography: Segoe UI Variable/Segoe UI/system; dialog title 18px weight 500; fields/body 14px; helpers and shortcuts 12px (11px minimum for compact accelerators); standard 4px spacing unit. Controls, button emphasis, focus, busy state, disabled state and icon stroke inherit the previous Buttons and Icons categories. Use 140ms optional appearance transitions, no bounce; reduced-motion is immediate. No transparent text surfaces or decorative saturated dialog headers.

## Meaningful content for shown workflows

**Extract/split:** title names the actual operation; header shows real source basename and page count. Labeled page range, concise syntax example, validated selected count, result destination and explicit source effect. Keep extract/split only if the existing workflow combines them. Primary verb follows selected mode. Parse the production engine's actual supported range grammar; preserve ordering/duplicate semantics. Show inline field errors and retain input. Verify whether split removes selected pages or copies them before stating source effects. A change to source needs clear copy; do not add a new confirmation to an already authorized routine workflow without a real need.

**Create PDF from images:** compact empty state with Add images and Paste/clipboard access only when available. After files arrive, display real thumbnails, basenames, page order and remove/reorder actions; keyboard reorder must be available. Show actual page count. Put JPEG quality under clearly named encoding options when useful. Preserve original data and DPI according to engine capabilities; never promise original encoding for unsupported formats or clipboard recompression. Validate required input, supported files, quality bounds and failures; show which file failed. Offer further Add images and clipboard actions after the first addition. The preview's single Add example images button and filenames are illustrative, not real file picking or the complete production control inventory.

**Stamp:** compact 2-column option grid with the existing stamps and a bounded preview that uses the actual stamp renderer. Keep all introductory text visible. Primary verb “Place on page” enters the existing placement mode; a clear cursor/placement cue and Escape behavior show what happens next. Preserve stamp dimensions, document units and actual save behavior; the screenshot's 480 × 200 px and bake-on-save statement must be verified from code, not assumed to be universal. Never recolor the rendered document stamps merely to match UI accent. Confidential red and Approved green describe stamp content, not UI status. Long/custom labels must fit.

**Selected annotation/text toolbox:** one shared surface with appropriate quick property, optional Comment, Delete and Done/Apply when existing editing is transactional. Cancel discards only the current draft if the engine supports that distinction. Do not rename Confirm to Done before auditing commit semantics. Distinguish text creation, text editing, annotation editing and immediate property changes. Keep delete's affordance separate from the primary commit button; preserve undo and the existing confirmation policy. Comments expand inside one surface or route to the authoritative review thread, with actual author/time/content, readable textarea and an enabled submit only for meaningful content. Avoid duplicating independent thread state in left panel, inspector and toolbox. Preserve IME/text-edit focus on canvas interactions.

**File/application/context menu:** inventory every current command first, including Close tab, Undo/Redo, OCR, theme, preferences, palette and updates. No feature is removed by the illustrative menu. Group file operations, editing, navigation/view, tools and application help using measured row count and readable separation. Use verified accelerators from the registry. Document-dependent items show actual capability and availability. Make disabled reasons available in an accessible description or contextual help; disabled menus must not produce unexplained silence. Ellipsis means another configuration/choice step, not every command. Checkmarks reflect actual toggles. Submenus retain clear arrows and keyboard routing. Use the same command ID across dock, palette, toolbar and menu.

## Overlay behavior contracts

Modal dialogs: correct dialog semantics/name/description; background inert; focus enters a meaningful first field or safe action; focus stays in the modal; Escape follows existing cancel/dirty-draft policy; close returns focus to opener. Don't apply modal focus trapping to ordinary menus or toolboxes. Avoid nested modals; where a native file picker is required, coordinate focus as a native child flow. Do not blanket-dismiss dialogs on backdrop click if it could lose input. Enter should trigger the primary action only where the current focused control permits it (never while composing IME or typing a multiline comment).

Menus: framework accessible menu primitive; arrow keys, submenu navigation, Home/End where appropriate, type-ahead if supported, Escape dismissal and return-to-opener. Outside click can dismiss without intercepting the underlying action unexpectedly. Disabled command handling must match primitive/platform conventions. Toolboxes/popovers: keyboard reachable, no modal trap, explicit focus return where meaningful, preserve canvas selection when interacting and never treat toolbar clicks as deselection. Escape closes the top applicable popover/draft according to the existing editor's state machine. Tooltips never obscure controls, carry essential instructions alone or demand focus traps.

Use a central overlay layer and named stacking tokens; let the existing framework establish actual z-index values. Account for canvas transforms, native app chrome and portal roots. Position relative to actual available editor bounds. On scroll/zoom, reposition or dismiss as appropriate, without creating detached toolboxes. Distinguish transient menu, nonmodal property popover, modal task and native child-dialog layers. Avoid solving stack conflicts with arbitrary ever-higher z-index values.

Forms need visible labels, truthful helper text, input validation near the relevant control and clear correction. Don't clear drafts on validation failure. Disabled primary actions explain prerequisites. Long-running operations use a stable-width busy action, prevent duplicate execution, show real progress when available and expose cancellation only if the engine supports it. Keep unsupported actions disabled/omitted according to existing product policy. Never show fabricated percentages, success or output size. On failure retain useful state and provide retry/recovery that invokes real handlers.

## Apply to every unseen surface

Assign each discovered overlay to one shared primitive: TaskDialog, PreviewTaskDialog, ContextToolbox, PropertyPopover, CommandMenu, Tooltip or existing NativeSystemDialog. Add per-task content through slots/schema; do not fork styling in individual feature components. Shared primitives define geometry, appearance and accessibility; task adapters own command binding, validation, capabilities and state. Some tasks such as signatures, encryption, redaction, destructive operations or authorization require their existing specialized wording and transaction safeguards; do not homogenize semantics or alter sensitive document behavior for visual consistency.

Acceptance: coherent light/dark appearance; meaningful content; no clipped header/body/footer; long localization; supported minimum window width; 100/125/150/200% scaling; keyboard/screen-reader operation; IME and multiline input; modal focus/background inertness; menu edge collisions; toolbox positions near page edges and across zoom/scroll; lossless draft cancellation; actual range/quality validation; busy duplicate guards; engine failures; native child-picker return. Compare screenshots across every primitive and ensure all registered commands remain reachable.
