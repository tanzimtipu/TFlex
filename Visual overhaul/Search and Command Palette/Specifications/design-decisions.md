# Search and Command Palette — Command Lens

Use one command registry, with separate **Tools** and **In document** modes. A command searches actions; document find searches PDF content. Keep their results, availability rules and state separate. The installed app exposes Search tools (Ctrl+K) and Find in document (Ctrl+F); reuse those commands and verify all other bindings in source. The title bar and dock must open the same tool palette.

Command Lens is a 560–640 logical-px anchored / modal command surface below the document rail, with a 44 px input and 52–60 px result rows. The alternative Search Drawer is a 320–360 px attached side surface for sustained searching while reading. Reserve the document viewport for the drawer; a floating palette is transient. Both use the same controller, registry, filtering and command IDs.

Rows contain a 20 px shared icon, clear action label, 12 px workspace / scope label and an actual accelerator where registered. Group only meaningful results; show recent commands only if usage history exists and its privacy rules are respected. Avoid popularity scores, artificial recommendations or AI sparkle decorations. Use violet only for the focused / selected result, with a programmatic active state. A disabled command explains its actual document capability or selection requirement.

Support keyword and available alias matching with stable ranking. Do not guess engine capabilities from extension or UI workspace. A query with no result says “No matching tools” and retains the query. Enter activates the focused supported command; arrows navigate; Escape closes and restores focus to the opener. Reuse accessible combobox / listbox primitives; avoid two competing keyboard handlers. Opening the palette does not reset PDF selection, viewport or undo history.

Document find shows real match counts, source page labels, snippet context and previous / next. Distinguish searching, matches, no matches and unavailable text. An image-only page should offer the existing text-recognition flow where supported, without claiming that running OCR is equivalent to finding text. Searches must be scoped to the current document unless an explicit supported wider scope is selected. Coordinate match highlights through the PDF viewport transforms; keep UI hover separate from persistent annotations. Preserve the correct current match after zoom, rotation, layout change and document switch; cancel obsolete search jobs. Very long documents may need incremental results; announce honest partial counts rather than a final count before completion.

Use 14 px query text, 13 px result labels and 12 px helper / shortcut text. Tooltips explain truncated titles and unavailable actions, not paragraphs of onboarding. Honor high contrast, reduced motion, keyboard composition and localized strings. Do not capture document typing globally when the palette is closed.

Acceptance: registered command availability, keyboard and pointer execution, query reset policy, Escape / focus return, zero results, disabled commands, scanned PDFs, delayed find, multiple documents, rotated / mixed-size pages, fit layouts, 200% scaling and dark / high contrast. Test result anchors against real PDFs; the prototype's three matches and snippets are explicitly schematic.

## Shared visual and implementation rules

This category extends Quiet Precision. Surface / canvas: #FFFFFF / #F5F6F8 in light, #20232B / #171A21 in dark. Main text: #485164 / #B8C0D0; strong: #232A38 / #EEF1F7; small supporting text: #667085 / #929BAC. Boundary: #E1E4EB / #3B414E; interactive violet: #7050D6 / #B9A4FF; selected surface: #F0EBFC / #302740. Read the unified semantic tokens and the Consistency Corrections folder. Document-tab identities remain colorful and stable per session, confined to the rail.

Use a 4 px spacing grid, 9 px control radius, 12–14 px floating surface radius, 16–24 px content spacing and 140 ms emphasis transitions. Attached panels use hairline boundaries, not floating shadows. UI typography follows the existing Typography folder. Original icons follow the 24-unit / 1.65 round-stroke grammar; this reference uses host Lucide icons for illustration. Never replace PDF fonts or pixels with UI tokens. Reduce motion and high contrast apply across the category.

First audit all relevant entry points, existing handlers, source data, capability predicates, settings / document stores, state transitions and any engine constraints. Reuse command / menu / dialog / form primitives; do not introduce parallel stores or CSS overrides at each call site. Only render information the app can support truthfully. This handoff designs behavior for capabilities to verify, not evidence that every pictured feature already exists.

Implementation phases: inventory and state contracts; shared primitives / tokens; category migration across every entry point; asynchronous and cross-document correctness; accessibility / performance; real app regressions and visual review. Preserve document content, session identity, undo history, keyboard bindings, permission checks, save / close / cancellation policies and native Windows chrome. Test all supported themes, long and localized labels, restored / maximized windows, 200% scaling, keyboard and relevant error / empty states.

## Reference limits

Both visual alternatives are local interaction prototypes. Filenames, people, comments, form labels, matches, progress, output geometry and command results are illustrative unless specifically documented as installed-app observations. They do not run OCR, PDF editing, conversion, save, print, mail, collaboration or system preference changes. The prototype's short fixture arrays and state handlers are not production data models. Example scenario controls such as Continue / Show failure on the Activity reference exist solely to inspect state styles and must not become product commands. Native dialogs, screen-reader tree semantics, forced colors, drag transforms, focus trapping and engine integrations must be implemented and tested with the real application.
