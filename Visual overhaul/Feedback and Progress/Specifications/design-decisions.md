# Feedback and Progress — Activity Shelf

Give asynchronous work a small, truthful home: an **Activity Shelf** anchored to the viewing footer, clear of the dock and page controls. Show a quiet summary while work is running; opening it reveals each real operation. The alternative Compact Notices favors small temporary completion notices with a discoverable activity list for longer jobs. Neither adds a permanent notification bell unless the app has a real notification model that needs one.

Operation rows use a 20 px task icon, 14 px task name, 12 px filename / scope and a supported cancellation action. Determinate progress uses known units and honest totals, such as “4 of 12 pages”. If totals are unknown, use indeterminate progress and phase text. Never invent a percentage or ETA. Success green, warning amber and danger red encode real state only; normal progress stays violet. The same operation cannot be Running and Completed in separate widgets.

Use operation IDs and revision-aware events. Model queued, running, cancellation requested, cancelled, completed, partial success and failed distinctly. Cancel requests must not claim cancellation before the engine confirms it. Disable duplicate starts only when necessary; keep unrelated documents usable. Attach operation context to its original document identity so switching tabs cannot redirect results or errors. For irreversible / non-cancellable work, label the limit truthfully instead of showing an inert Cancel.

Completion notices state what happened and offer a meaningful supported action: Open result, Show in folder, View details or Undo only when that operation has a real reversible transaction. Save succeeds only after storage confirms it; generating a PDF in memory is not a saved file. Do not discard user work on error or hide recoverable error details behind a short disappearing toast. Errors persist until acknowledged / resolved; Retry uses retained inputs only when safe and supported. Partial success lists failed items and permits a deliberate retry, never silent duplication.

Normal success notices may dismiss after a reasonable configurable interval; pause dismissal on hover, focus and accessibility interaction. Never time out a required user decision. Use polite announcements for completion and stage changes; alert only for actionable failures. Announce neither each percentage point nor every background event. Focus stays on the user's task unless intervention is required. Returning from Details restores focus.

Suggested geometry: 360–420 px floating activity surface, 12 px radius, one restrained shadow, 12–16 px spacing, 6 px progress track. On constrained windows use a bounded sheet with content scrolling; reserve safe footer / dock geometry. Status text elsewhere in the app follows this model rather than duplicating unrelated success colors.

Acceptance: known / unknown totals, one / many concurrent jobs, tab switch / close, app minimize / restore, cancellation races, failure / retry, partial success, save failure, completed output opening, keyboard focus, screen-reader announcements and dark / high contrast. The prototype advances a fixture job with explicit example controls; those controls are not production commands and must not be copied into the product.

## Shared visual and implementation rules

This category extends Quiet Precision. Surface / canvas: #FFFFFF / #F5F6F8 in light, #20232B / #171A21 in dark. Main text: #485164 / #B8C0D0; strong: #232A38 / #EEF1F7; small supporting text: #667085 / #929BAC. Boundary: #E1E4EB / #3B414E; interactive violet: #7050D6 / #B9A4FF; selected surface: #F0EBFC / #302740. Read the unified semantic tokens and the Consistency Corrections folder. Document-tab identities remain colorful and stable per session, confined to the rail.

Use a 4 px spacing grid, 9 px control radius, 12–14 px floating surface radius, 16–24 px content spacing and 140 ms emphasis transitions. Attached panels use hairline boundaries, not floating shadows. UI typography follows the existing Typography folder. Original icons follow the 24-unit / 1.65 round-stroke grammar; this reference uses host Lucide icons for illustration. Never replace PDF fonts or pixels with UI tokens. Reduce motion and high contrast apply across the category.

First audit all relevant entry points, existing handlers, source data, capability predicates, settings / document stores, state transitions and any engine constraints. Reuse command / menu / dialog / form primitives; do not introduce parallel stores or CSS overrides at each call site. Only render information the app can support truthfully. This handoff designs behavior for capabilities to verify, not evidence that every pictured feature already exists.

Implementation phases: inventory and state contracts; shared primitives / tokens; category migration across every entry point; asynchronous and cross-document correctness; accessibility / performance; real app regressions and visual review. Preserve document content, session identity, undo history, keyboard bindings, permission checks, save / close / cancellation policies and native Windows chrome. Test all supported themes, long and localized labels, restored / maximized windows, 200% scaling, keyboard and relevant error / empty states.

## Reference limits

Both visual alternatives are local interaction prototypes. Filenames, people, comments, form labels, matches, progress, output geometry and command results are illustrative unless specifically documented as installed-app observations. They do not run OCR, PDF editing, conversion, save, print, mail, collaboration or system preference changes. The prototype's short fixture arrays and state handlers are not production data models. Example scenario controls such as Continue / Show failure on the Activity reference exist solely to inspect state styles and must not become product commands. Native dialogs, screen-reader tree semantics, forced colors, drag transforms, focus trapping and engine integrations must be implemented and tested with the real application.
