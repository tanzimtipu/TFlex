## Phase 88 - Sanitize PDF: strip active content (FEA-037, commissioned via TFL-315 / TFL-463, 2026-10-03)

**Operator request (product terms, TFL-463):** give TFlex users a **Sanitize** action: choose which classes of active/executable content to strip (JavaScript, launch/open actions, embedded files, metadata), run it on the active document, and get an **honest per-class report of exactly what was removed**, so a PDF received from an untrusted source can be made safe in one action. Offline only; no network feature.

**Relationship to Phase 54/57 (PDF/A + PDF/X validation), Phase 52 (encryption) and the save path (`serializeDoc`).** The validator already **detects** the exact classes this feature removes: `collectJavaScript` (`validation/pdfa.ts:316`), `collectExternalContent` (`validation/pdfa.ts:336`, via the `EXTERNAL_ACTIONS` set at `:118` covering Launch/URI/GoToR/SubmitForm/ImportData), embedded file specs, and the XMP reader (`validation/xmp.ts`). The sanitizer **reads** with those same predicates but must go further: it **removes** the carriers from the working document so a subsequent save writes a clean file. This phase adds one pure shared module, the shared contract, one new main-process sanitize service, one engine op / one IPC channel, the preload/main wiring, one persisted settings field and one renderer dialog. It adds no window, no new document model and no network.

**Capability boundary (honest, non-negotiable).** Sanitize removes the **document-structure** carriers of active content: the catalog `/Names /JavaScript` name tree, a JavaScript `/OpenAction`, JavaScript `/AA` (additional-action) entries, launch/URI/GoToR/SubmitForm/ImportData actions reachable from the catalog, a page `/AA` and an annotation `/A`, the `/Names /EmbeddedFiles` name tree, file-specification attachments (`/FS`), and the document metadata (the catalog `/Metadata` XMP packet - the metadata carrier the save path actually persists via `carryCatalogEntries`, `engine.ts:5871`). It does **not** rewrite page content streams (Phase 84/86 own that), and it does not remove the app's own `Producer`/`Creator` brand stamp that Phase 49 (`stampBrandMetadata`, `engine.ts:5519`) writes on every save - the report states that explicitly rather than claiming a total metadata wipe. Anything the sanitizer cannot interpret or remove is **reported, never silently dropped**. Because the serializer already carries only `/Names /JavaScript` and a `/GoTo` `/OpenAction` into the output (`carryCatalogEntries` / `carryJavaScriptNames`, `engine.ts:5871`/`:5909`), the persisted effect is strongest for the JavaScript tree and the XMP `/Metadata` packet; sanitize still removes every selected carrier from the working document and reports each one, and the report states the per-class count so it never implies more was stripped than was present.

**CTO RULINGS:**

1. **Scope is one new pure shared module, the shared contract, the main-process sanitize service + one engine op + preload/main wiring, one persisted settings field, and one renderer dialog.** Files: `src/shared/sanitize.ts` (new, pure), `src/shared/types.ts` and `src/shared/ipc.ts` (contract), new `src/main/services/sanitize.ts` (the pdf-lib reader/remover), `src/main/services/engine.ts` (the op), `src/main/index.ts` (handler), `src/preload/preload.ts` (bridge), `src/main/services/settings.ts` (the field), new `src/renderer/components/SanitizeDialog.tsx`, `src/renderer/state/toolsRegistry.ts`, `src/renderer/App.tsx` and `src/renderer/engine/{engineClient,types,stubEngine}.ts`. No new window, no new document model, no second settings channel, no network.
2. **One shared, pure source of truth for the class/option model and the report maths.** New `src/shared/sanitize.ts`, pure (no `fs`, no Electron, no DOM, no pdf-lib), mirroring `src/shared/redaction.ts` / `blankPages.ts` discipline. It exports `type SanitizeClass = 'javascript' | 'launchActions' | 'embeddedFiles' | 'metadata'` and the ordered `SANITIZE_CLASSES: readonly SanitizeClass[]`; `interface SanitizeOptions { javascript: boolean; launchActions: boolean; embeddedFiles: boolean; metadata: boolean }` and `DEFAULT_SANITIZE_OPTIONS` (all four `true` - the safe default); `normalizeSanitizeOptions(raw: unknown): SanitizeOptions` (preserve-if-valid per key, missing/invalid -> default); `interface SanitizeFinding { class: SanitizeClass; where: string; detail: string }` (one per removed item, `where` readable, e.g. `catalog /OpenAction` or `page 3 annotation 1`); and `summarizeSanitize(findings: readonly SanitizeFinding[], options: SanitizeOptions): SanitizeReport` returning `{ selected: SanitizeClass[]; removedByClass: Record<SanitizeClass, number>; findings: SanitizeFinding[] }`. Every function is unit-tested directly with no PDF.
3. **The main-process sanitize service reads with the existing validator predicates and removes from the working `PDFDocument`.** New `src/main/services/sanitize.ts` exporting `stripActiveContent(doc: PDFDocument, options: SanitizeOptions): { report: SanitizeReport; warnings: string[] }` (mutates `doc`). It reuses `collectJavaScript` / `collectExternalContent` / the `EXTERNAL_ACTIONS` set from `./validation/pdfa` for the detection predicates (no fork of that logic) and removes: `javascript` - the catalog `/Names /JavaScript` key (prune `/Names` when it becomes empty), a JavaScript `/OpenAction`, and catalog/page/annotation/AcroForm/field `/AA` entries whose `/S` is `/JavaScript`; `launchActions` - `/OpenAction`, page `/AA` and annotation `/A`/`/AA` actions whose `/S` is in the canonical external-action set (`EXTERNAL_ACTIONS`: `/Launch`, `/URI`, `/GoToR`, `/SubmitForm`, `/ImportData`, `/GoToE`), leaving a benign `/GoTo` (internal navigation) alone; `embeddedFiles` - the catalog `/Names /EmbeddedFiles` key, annotation `/FS` entries, `/FileAttachment` annotations' file specs, and a `/Launch` action's `/FS`; `metadata` - the catalog `/Metadata` XMP packet. Every successful removal appends a `SanitizeFinding`; every object the service cannot interpret (wrong-typed value, malformed name tree, an action dict with no readable `/S`) appends a readable `warnings` entry naming the location - never a silent skip.
4. **One new engine op and one new IPC channel.** `engine.sanitizeDoc(docId, payload)` on channel `engine:sanitize`. `SanitizePayload { options: SanitizeOptions }`. It returns `Result<SanitizeResult, EngineError>` where `SanitizeResult { state: EngineState; report: SanitizeReport; warnings: string[] }`. The op validates `options` via `normalizeSanitizeOptions`, takes exactly ONE `snapshotDocWithPdf` before any mutation (so a sanitize is one undo entry), calls `stripActiveContent` on `doc.pdfDoc`, pushes the snapshot, sets `doc.modified = true`, and is enqueued through `_enqueue` like every other mutating op. No new `EngineError` member is required: an all-false selection is the existing typed `no-op`, and a document whose catalog cannot be read is the existing typed `engine-error`.
5. **Metadata boundary is stated, not over-claimed.** The `metadata` class removes the catalog `/Metadata` XMP packet from the working document; the serializer carries `/Metadata` from the live working document (`carryCatalogEntries`, `engine.ts:5871`), so removing it from `doc.pdfDoc` persists, and the report names the XMP packet as the removed metadata carrier. The legacy source `/Info` string dictionary is not carried by the normal save path, so it is out of scope. The Phase 49 brand stamp (`stampBrandMetadata`, `engine.ts:5519`, called from `serializeDoc` at `engine.ts:6590`) always writes `Producer`/`Creator` = `Jovrel`; that stamp is **not** removable by sanitize and the report wording says so. No change to `serializeDoc` or `stampBrandMetadata` is in scope.
6. **Fail-loud, never a silent no-op.** Per-object failures are collected in `warnings` with a readable location and returned in `SanitizeResult.warnings`; the renderer shows them in `[data-sanitize-report]` (never blank after a run). An all-false selection returns the typed `no-op` with a readable message and mutates nothing. Every selected class that removed zero items is reported as `0` - the report never implies removal that did not happen.
7. **The sanitize options are a persisted setting.** `AppSettings.sanitizeOptions?: SanitizeOptions` (default `DEFAULT_SANITIZE_OPTIONS`, all four true), validated preserve-if-valid per key in `src/main/services/settings.ts` `normalizeSettings` (mirror `normalizePdfValidationDefaults`, `settings.ts:745`), transported over the existing AppSettings IPC. The dialog reads it for its initial checkbox state and writes it back through the existing settings path; no new settings channel and no credential.
8. **No regression** to normal open/save, the PDF/A + PDF/X validation (which must still DETECT JavaScript/actions/files on a file that carries them, and report clean on a sanitized file), encryption (Phase 52), redaction (Phase 84), search/replace (Phase 86), blank-page removal (Phase 87), annotations, forms/signatures, or settings persistence. The feature is fully offline (no network call, nothing leaves the machine).

**Success criteria**

1. The Sanitize dialog lets the user select any combination of the four classes (JavaScript, launch/open actions, embedded files, metadata) and run sanitize on the active document; the selection persists across restart.
2. Sanitize removes the selected class carriers from the saved file and reports, per class, what was removed (`removedByClass` counts plus a per-item finding list); after save + reload the removed carriers are absent (re-read with the validator's `collectDocumentFacts`) while unselected classes and page content are unchanged.
3. Fail-loud, honest reporting: every object the sanitizer could not interpret or remove appears in `[data-sanitize-report]` / `[data-sanitize-warning]` with a readable location, never silently dropped; an all-false selection is refused with the typed `no-op`; a class that removed nothing reports `0`.
4. Offline only: no network, cloud, accounts or subscriptions; the feature adds no network call.
5. No regression to normal open/save, PDF/A + PDF/X validation (a sanitized file validates clean; an unsanitized file is still detected), encryption, redaction, search/replace, blank-page removal, annotations, forms/signatures or settings persistence.
