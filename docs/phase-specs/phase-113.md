## Phase 113 - Buttons overhaul: the Quiet Actions shared button system applied app-wide (phase issue TFL-839; operator driver TFL-812, 2026-10-06)

**Operator request (product terms, TFL-812 / phase issue TFL-839).** Replace TFlex's mixed,
ad-hoc button treatments with the committed Visual overhaul **Quiet Actions** family
(`Visual overhaul/Buttons/`), app-wide: one framework-native button primitive with explicit
semantic kind, intent, density, icon/text content and states, consumed consistently across
Home, the title bar, tabs, the dock, panels, inspectors, dialogs, menus/context menus, empty
states and notices. It must match the established Quiet Precision icons, Focus Dock and
Context Pair panels and keep the app ultra-modern, simple and elegant. No command, shortcut,
handler, selector, document operation or undo/redo behaviour changes. Precedence: consistency
corrections > button design spec > visual references. Operator charge: "no conflict or
overlapping contents." Out of scope: network features (offline-first).

**CTO rulings:**

1. **Scope.** Renderer only: `src/renderer/components/**`, the button/interaction sections of
   `src/renderer/styles.css`, `docs/BUTTON-SYSTEM.md`, and renderer unit tests. The shared
   button primitive already exists from Phase 91 (`Button`/`IconButton` in
   `src/renderer/components/Button.tsx` plus the `.btn` family in `styles.css`); this phase
   EXTENDS and re-maps it onto the Quiet Actions specification - it does NOT fork a second
   button system. No `src/main/**`, no `src/shared/**`, no IPC, no settings channel, no new
   dependency, no network call. qa owns `e2e/**`, `screenshots/**`, `test-fixtures/**`.
2. **One primitive, explicit taxonomy.** One button primitive with explicit intent
   (primary / secondary / tertiary / destructive), semantic kind
   (action / toggle / exclusive-selection / disclosure), density
   (compact / standard / prominent / coarse) and content (icon / text / icon+text). Specialized
   dock tiles, view segments, menu actions and native caption controls remain specialized
   consumers with their own geometry; do not force native window controls into generic rounded
   rectangles or replace native controls with a web layer.
3. **Inventory before replacement.** Record every interactive control across Home, title bar,
   tabs, dock, panels, inspectors, dialogs, menus/context menus, empty states and notices,
   including controls unseen in the screenshots: command ID, action/disclosure/toggle
   semantics, emphasis, density, states, labels, actual shortcuts and handlers. Resolve
   ambiguous title-bar Save / Save As / Save All variants and mode controls from their
   handlers, never by guessing. Audit controls absent from the references.
4. **Consistent treatments.** Primary = solid shared violet with a contrasting label for the
   single main task action (Open files, Export PDF), one primary per action group, not every
   section; Secondary = neutral surface, subtle boundary and graphite content (Create PDF from
   images, Merge PDFs, Add text box, Apply page label); Tertiary/utility = transparent graphite
   with neutral hover (Tools, More, subordinate Cancel, contextual utilities); Persistent
   tools/views = soft violet selected tile whose pressed/selected state is read from real app
   state; Destructive = red label/icon with subtle red hover for actual delete commands, a solid
   danger commit only where an existing destructive flow already needs one.
5. **Colour discipline.** Do not colour ordinary merge/export/insert buttons green; reserve
   green for genuine success feedback. Normal one-shot commands must not stay selected after
   clicking. Identify ambiguous title-bar save variants and mode controls from handlers before
   renaming or restyling their semantics; security/protection actions (e.g. Encrypt) are
   ordinary commands until their real semantics warrant a different state.
6. **Geometry and motion.** Inherit the 9 px control radius, 6 px icon-label gap, 4 px spacing
   unit and existing icon grammar: standard buttons ~36 px content-driven height with 12 px
   medium labels and 12 px horizontal padding, compact utilities 32 px where native chrome
   permits, prominent actions 40 px, at least 44 px effective coarse-input targets. Dock tiles
   keep their existing 20 px icons / 12 px labels and layout. Icons are theme-bound vector
   glyphs; centre the combined icon-label content. Add primary hover/pressed shades from the new
   tokens and keep readable foregrounds in both themes. Keep buttons flat, with elevation on
   containing dock/popover surfaces. Use 140 ms colour/background/border transitions with
   reduced-motion support; no magnification, bounce, ripples, gradients or decorative icon
   animation. Keep a distinct focus ring that works with selected states and high contrast.
7. **State and capability honesty.** Disabled controls remain legible and carry an accessible
   reason where useful - never nearly invisible, never dependent on hover over a native disabled
   button. Hide irrelevant actions and disable relevant unavailable actions per the real
   capability model. Busy actions expose operation state, prevent duplicate activation in both
   UI and handler, preserve focus where possible and reserve width for localized resting/busy
   labels. Completion/failure goes to an existing status area; do not permanently turn commands
   green or claim completion before the backend succeeds.
8. **Preserve behaviour and semantics.** Keep concrete labels and actual Windows shortcuts;
   preserve specialist text labels, tooltip/accessibility names, native title-bar
   drag/system/caption behaviour and tab-close semantics. Full-width buttons only for purposeful
   vertical action layouts, not every property. Long/localized labels reflow or use established
   overflow rather than shrinking into illegibility. Disclosures use real menu primitives with
   expanded state, focus navigation, Escape/focus return, outside dismissal and screen-bound
   positioning. Action groups are not exclusive toggles unless the model actually is. Preserve
   existing dialog ordering/default-action conventions and destructive-action safeguards; no
   extra approval step is part of this visual task.
9. **Validation and evidence.** Validate all intents and semantic kinds in light / dark / high
   contrast, Windows 100/125/150/200% DPI, keyboard and touch, localization/text scaling,
   narrow/resized-panel layouts and busy/error/success conditions; check contrast of normal text
   and essential indicators, no label/width jumps, no double execution or focus loss, and
   correct persistent selection from app state. Deliver the complete button inventory/mapping,
   primitive/token changes, representative before/after screenshots and validation results,
   clearly identifying any unresolved controls outside the screenshot set.
10. **No overlap and flow.** Consume the shared Quiet Precision icon registry as the single
    source of truth; do not fork a second icon or button visual language, and do not restyle
    dock organisation, panel structure or navigation structure. The phase starts after the
    sibling visual-overhaul phases have closed and committed, so git-agent commits stay
    role-clean. Flow: CTO brief -> frontend-dev -> focused qa verification and visual verdict ->
    adversary diff-pass -> phase-close QA verdict -> ONE local phase-close commit via git-agent;
    no push, release, tag or credential change without explicit operator approval.
