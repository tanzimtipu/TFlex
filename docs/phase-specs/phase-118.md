## Phase 118 - Drag Drop and Import overhaul: the Intake Tray (phase issue TFL-1230; CEO commission from TFL-1223, 2026-10-08)

**Operator request (product terms, TFL-1230 / category handoff `Visual overhaul/Drag Drop and Import/`).** Unify every file-intake entry point - Home, Open, canvas drops from Explorer and "Create PDF from images" - under ONE truthful **Intake Tray** surface so drag-drop and import behave as one consistent system. **Compact Intake** is a layout alternative only and, if supported, must reuse the same state and handlers, never a second subsystem. Truthfulness gates acceptance: actions depend on real content / engine detection and permission, never on a file extension alone; there is no bogus "Ready" on an unknown file; every mixed / unsupported / misleading-extension / unreadable / protected input gets an explicit per-item error while supported choices stay visible through a partial failure; the queue shows basename, detected supported type, state and Remove from queue (removal is not file deletion), keeps the user's order, uses safe text nodes with accessible full locations rather than giant path rows, and never silently alphabetizes or duplicates. PDF files may open as separate sessions; an image collection may build ONE PDF through the existing image-creation pipeline; where more than one operation is plausible the intake asks with meaningful choices and never infers a destructive replacement from the pointer's location. A subtle drop indication appears only while an eligible OS file drag enters the application. Drag-and-drop is never required: a labeled native picker and the supported clipboard flow stay accessible. The flow is offline-only - no network, remote collaboration, conversion service, mail or print execution from this surface. Precedence: live-app refinements > design-decisions > illustrative visuals; Consistency Corrections and the unified semantic tokens stay in force; original PDF pixels are never recolored and a document is never mutated merely by selecting a view or configuring options.

**CTO rulings:**

1. **Scope.** Renderer only: `src/renderer/hooks/useOsIntegration.ts` (`useOsFileDrop` `:80`, `useOsOpenPathRequests` `:134`, `isFileDragEvent` `:31`, `resolveDroppedPath` `:49`), a new `src/renderer/intake/` module (the ONE intake model + surface), `src/renderer/components/Welcome.tsx` (hero intake surface only), `src/renderer/components/CreateFromImagesDialog.tsx` (queue unification only), `src/renderer/App.tsx` (intake wiring / open + create routing only), `src/renderer/state/convert.ts` (reuse; extend classification helpers only), `src/renderer/utils/pickImageFiles.ts` (reuse), `src/renderer/styles.css` intake section, and renderer unit tests. qa owns `e2e/**`, `screenshots/**`, `test-fixtures/**`. **No `src/shared/` contract change, no new IPC, no new `AppSettings` field, no dependency, no network, no backend chunk**: every operation the intake dispatches already exists (`openPdfFromPath` `App.tsx:2574` -> `routeOpenPath` `convert.ts:148`; conversion bridge `convert:sourceInfo` / `convert:toDocument` / `convert:toDocumentMany`; `createFromImagesRoute` `convert.ts:353`; `clipboard:readImage`; `openFilesDialog` `src/shared/ipc.ts:1154`).
2. **One intake model, no forks.** The new `src/renderer/intake/` module owns ONE reducer-free ordered queue of intake items (basename, resolved path/File, detected type, state, error) and ONE dispatcher that routes each item to the REAL existing operation: PDF -> the shared open path as its own session; recognized convertible -> the existing conversion route; image collection -> `createFromImagesRoute`. It never introduces a second document store, a second settings store, or per-call-site CSS overrides. The `CreateFromImagesDialog` queue becomes a consumer of this same model rather than its own `useState<File[]>` list; the Home surface and the drop surface consume the same model. No placeholder commands, no prototype fixture records, no scenario buttons ported from the prototype.
3. **Detection is content/engine-based, never extension-trust.** Classification uses `convert.sourceInfo(path)` and real byte/magic detection, not just the filename: a mislabeled/truncated/unreadable file reports its real failing state (mirroring `toastForConvertError` `convert.ts:77`, `unsupportedFileMessage` `:116`, `associationMessageFor` `:120`), never a fabricated "Ready". A file with a misleading extension is shown as its detected type or an explicit error.
4. **One / many / order.** A drop or picker selection of many PDFs opens each as its own session in selection order; an image collection produces ONE PDF in list order; mixed selections route each item by type and keep successes visible while failed items stay in the queue with their error. The current `useOsFileDrop` "open the FIRST file, toast the rest" behaviour (`useOsIntegration.ts:95-110`) is replaced by this routing. Duplicate basenames are disambiguated, never merged or dropped.
5. **Truthful states.** Empty / validating / ready / converting / failed-partial / completed are real and driven by the actual operation (progress from `convert:progress`, `onProgress` `convert.ts:214`); async presentation reuses the Feedback and Progress / Activity Shelf primitives (TFL-1216) rather than a new progress surface. A cancelled conversion (`cancelled` in `convert.ts:97`) is quiet and leaves the app as it was. Clipboard failure explains the missing / unsupported clipboard (`CreateFromImagesDialog.tsx:115-126`) instead of creating an empty PDF.
6. **Live-app addendum precedence.** The image surface keeps a concise empty intake state that grows into an ordered preview queue; keeps Add images + clipboard actions, the actual supported types (JPEG/PNG), order, disabled completion (`valid` `CreateFromImagesDialog.tsx:223`), and new-tab creation semantics (`onCreateConfirm` `App.tsx:6065`); places recompression quality under image settings with the accurate help already present (`CreateFromImagesDialog.tsx:534-538`, "images added from disk keep their original quality and DPI") and never implies every disk input is recompressed. The Home empty state is the concise intake surface, not an oversized blank body.
7. **Entry points preserved.** All existing entry points keep working and keep their command IDs: Home fixed Open tile and the `homeTools` row (`Welcome.tsx:365-399`; wiring `App.tsx:11735`), `onOpenClick` (`App.tsx:2656`), the OS-open path (`App.tsx:2648`), recents (`App.tsx:2713`), `CreateFromImagesDialog` mount (`App.tsx:12504`), and the multi-select `openFilesDialog` used by merge-from-scratch (`mergeFromScratch.ts:34`). The intake is additive and unifies them; it removes none.
8. **Out of scope (unsupported, recorded, never faked).** No network / remote / conversion service / mail / print execution from the intake; no arbitrary path evaluation or embedded-content execution during previews; "insert pages into the current document" is offered only if a real engine operation exists - the current contract exposes no insert/append-from-file op (`createFromImages` is the only image path in `src/shared/types.ts`), so it is a capability-backed extension if the engine later gains it, and the intake must not present a dead control. XFA, DRM e-books (`convert.ts:88`) and unsupported formats keep their existing truthful refusals.
9. **Seams reconciled, never duplicated.** Feedback and Progress / Activity Shelf (TFL-1216) owns async progress / failure - reuse. Responsive and Accessibility / Adaptive Shell (TFL-1224) owns global responsive / accessibility rules - apply, do not fork. Dialogs, Toolboxes and Menus owns modal mechanics - reuse DialogShell / the existing dialog primitives. Forms and Validation / Guided Fill (Phase 115) owns the CSV/FDF/XFDF form-data workflow - the intake must not fork it. Selection and Manipulation (Phase 117) + Thumbnails and Outline own page / object drag - file intake stays distinct from page transfer. Print and Output / Output Studio (TFL-1225) owns print execution - the intake never prints. Document-tab identities stay colorful and stable, confined to the rail.
10. **Accessibility, adaptation and pixels.** The intake tray has complete labels and roles, keyboard alternatives for every action (picker, clipboard, remove, reorder), transient focus / Escape, screen-reader names for rows and errors, forced-colors / high contrast, reduced motion, resize / theme adaptation, long / localized labels, narrow supported windows and 200% scaling. Selecting an item or configuring the tray never recolors a PDF pixel or changes document content; UI typography never becomes a document font. Preserve session / selection identity, undo / draft semantics, permission checks, save / close / cancellation policy and native Windows chrome.
11. **Controls.** Every intake control keeps a real production handler proven by a named test (see CONTROL-INDEX). Removal removes from the queue only - never a file deletion; there is exactly one clipboard entry and one picker entry per surface.
12. **Intake dispatch trigger - explicit completion, never auto-open (CTO ruling 2026-10-08, resolves TFL-1325).** The intake queue is a STAGING surface: adding a file (picker, OS / canvas drop, clipboard) never opens, converts or mutates a document at the call site, and no document is opened merely because it entered the queue. The Intake Tray owns exactly ONE completion control (`data-intake-open`) that IS the dispatch trigger: disabled when the queue has no `ready` item and while the whole queue is busy (`validating` / `converting`), enabled otherwise. Activating it calls the existing `IntakeModel.dispatch` with the real operations the host injects - each `ready` PDF -> the shared open path (`openFromRequest` `App.tsx:2812`) as its own session in queue order; a `ready` image set -> the existing image-creation pipeline (`runCreateFromImages` `App.tsx:6275` -> `createFromImagesRoute` `convert.ts:360`) as ONE PDF in queue order. `convertible` / `unknown` items are not dispatched (the host owns their conversion route) and, together with `failed` items, stay in the queue with their truthful error while successes remain visible (partial failure); successfully dispatched items leave the queue. `converting` / `done` / `failed` are driven ONLY by this real dispatch (`begin` / `settle`), never by `add` / `classify` alone. `CreateFromImagesDialog`'s existing `Create PDF` button (`data-create-confirm`) remains the completion control for its own queue and routes through the SAME `runCreateFromImages` / `createFromImagesRoute` - no second pipeline. Chunk D's entry-point contract stands unchanged: entry points stage into the queue; the Tray's completion control is the only trigger that opens.

**Success criteria**

1. **One intake surface.** Home, Open, canvas / OS drops and Create PDF from images all route through the ONE `src/renderer/intake/` surface sharing the same state and handlers; Compact Intake (if present) reuses that state; no second subsystem, store or per-call-site CSS override; no prototype fixture record or scenario command in production.
2. **Picker / drop equivalence.** The native picker, the clipboard flow and a drop feed the same intake queue and produce the same result for the same inputs; drag-and-drop is never required.
3. **One / many / order / duplicates.** A selection or drop of many PDFs opens each as its own session in order; an image collection builds ONE PDF in list order; duplicate basenames are disambiguated, never merged or dropped; the queue order is preserved and reorderable by mouse and keyboard.
4. **Truthful detection and states.** Item actions are based on real content / engine detection and permission, not extensions; no bogus "Ready"; empty / validating / ready / converting / failed-partial / completed are real and reuse the Activity Shelf; a cancelled conversion is quiet and leaves the app unchanged.
5. **Errors and partial failure.** Mixed / unsupported / misleading-extension / unreadable / protected inputs and clipboard failure each produce a specific, truthful message; supported inputs stay usable and successes remain visible through a partial failure; no empty PDF is ever synthesized.
6. **Images semantics.** The image surface keeps a concise empty state that grows into an ordered preview queue, reuses the existing image creation pipeline, keeps disabled completion and new-tab creation semantics, and places recompression quality under image settings with accurate help that never implies every disk input is recompressed.
7. **Entry points preserved.** Every existing entry point and command ID keeps working (Home Open tile and `homeTools`, `onOpenClick`, OS-open path, recents, `CreateFromImagesDialog`, multi-select `openFilesDialog`); the intake adds, it does not remove; removal from the queue is never a file deletion.
8. **Offline and boundaries.** No network, remote collaboration, conversion service, mail or print execution from this surface; no arbitrary path evaluation or embedded-content execution during previews; unsupported operations (e.g. insert-into-current-document without an engine op) are recorded extensions, never dead controls.
9. **Pixels, content and identity.** Intake never recolors a PDF pixel, mutates a document, or marks a document dirty merely by adding to or configuring the queue; session / selection identity, undo / draft semantics, permissions, save / close / cancellation policy and native Windows chrome are preserved.
10. **Accessibility and adaptation.** Complete labels and roles, keyboard alternatives for picker / clipboard / remove / reorder, transient focus / Escape, screen-reader names, forced-colors / high contrast, reduced motion, resize / theme adaptation, long / localized labels, narrow supported windows and 200% scaling hold.
11. **Seams.** Async progress / failure reuses the Activity Shelf; global responsive / accessibility rules are applied from Adaptive Shell, not forked; modal mechanics reuse DialogShell; the form-data (CSV/FDF/XFDF) workflow stays with Guided Fill; page / object transfer stays with Selection and Thumbnails; print stays with Output Studio; document-tab identities stay colorful and confined to the rail.
12. **Evidence and flow.** The inventory document, files changed per role, CONTROL-INDEX sweep, focused test runs (command + counts), full and compact screenshots in every theme plus high contrast and 200%, and the unsupported-capability list are delivered; standard flow CTO (A) -> frontend-dev (B-F) -> focused qa (G) -> adversary diff-pass (H) -> phase-close QA (I) -> ONE local commit via git-agent (J); no push, release or credential change without explicit operator approval.
