## Phase 115 - Forms and Validation overhaul: Guided Fill (phase issue TFL-1227; CEO commission from TFL-1218, 2026-10-08)

**Operator request (product terms, TFL-1227 / category handoff `Visual overhaul/Forms and Validation/`).** Give Forms and Validation one consistent, truthful **Guided Fill** surface: separate **Fill form** from **Edit form fields**, one shared state and one renderer for every form entry point. Guided Fill helps a user complete values on an existing PDF form with a visible current field, real document/page scope and a required-field summary; **Field Inspector** is the layout alternative and must reuse the same state and handlers, never a second subsystem. Truthfulness gates acceptance: use real AcroForm metadata only (`/Ff` Required bit, `/TU` tooltip / real field name); never synthesize labels, required flags or email semantics from nearby page text or a screenshot; "complete" means the supported constraints passed, not merely non-empty; keep **form-value validation** distinct from **document-conformance validation** (PDF/A, PDF/X); preserve every widget type, export value, option label, radio grouping, multiselect, appearance stream, field name, read-only flag and document permission; unsupported field types show a useful read-only explanation and are never silently converted; ordinary filling never flattens; never claim a signature is verified or legally valid; preserve the app's existing PDF-script policy. Precedence: live-app refinements > design-decisions > illustrative visuals; Consistency Corrections and the unified semantic tokens stay in force. Out of scope: any network/email delivery; new document-conformance surfaces.

**CTO rulings:**

1. **Scope.** Renderer: `src/renderer/forms/**` (new Guided Fill primitives + surfaces), `src/renderer/App.tsx` (the forms wiring and the `forms`/`flatten`/`fillFromCsv`/`exportFormData`/`importFormData`/`validateDocument` action handlers only), `src/renderer/components/Inspector.tsx` / `ContextPanel.tsx` forms rows, `src/renderer/styles.css` forms section, renderer unit tests, and the inventory doc under `docs/`. Shared contract: an additive extension of the existing `FormField` shape in `src/shared/types.ts` only. Backend: `src/main/services/forms.ts` (read the new metadata) and its unit tests. **No new IPC channel** - extend the existing `engine:getFormFields` payload. No new `AppSettings` field, no dependency, no network. qa owns `e2e/**`, `screenshots/**`, `test-fixtures/**`.
2. **One surface, no forks.** Migrate every form entry point onto the single Guided Fill surface backed by the existing per-tab `FormsState` (`src/renderer/forms/model.ts`). Reuse the shipped primitives - `DialogShell`, `Button`/`IconButton`, `Icon`, `TfResize`, Phase 100 `src/renderer/design` tokens, the Panels Context Pair chrome, and the Activity Shelf operation-state primitives. Do not introduce a parallel store, a second reducer, or per-call-site CSS overrides.
3. **The `forms` verb is a lie today.** `src/renderer/App.tsx:10767` wires the registry entry `forms` (label "Forms", "Fill AcroForm fields. Flatten when finished.") to `setFlattenOpen(true)` - the same handler as the separate `flatten` verb at `:10768`. The migration must point `forms` at the real Guided Fill surface and leave `flatten` on its explicit confirmation flow (`FlattenConfirmDialog.tsx`, `onFlattenConfirm` at `App.tsx:4726`).
4. **Inventory before migration.** Record every real entry point, its renderer component, command/registry id, `dockAppActions`/`paletteAppActions` handler, engine/IPC handler, capability predicate, authoritative metadata source, document store and async state transition - and classify each supported / needs capability-backed extension / unsupported. Map the observed Review commands (Forms, Flatten, CSV mapping, FDF/XFDF form-data import/export, PDF/A/PDF/X validation) to their real handlers. Resolve from live code, never by guessing.
5. **Truthful metadata only.** "Required" is `/Ff` bit 2 (Required) read from the field dictionary - never inferred. Accessible names come from the real `/TU` tooltip or the field name, with a truthful fallback; the bundled `form.pdf` generic names ("Text", "Checkbox", "Dropdown") are an observation, not a target. Email validation appears only when the field actually carries a supported constraint; if the engine cannot read such a constraint, email validation stays unsupported and is listed, not rendered. "Complete" means the supported per-field constraint passed, never merely non-empty.
6. **Validation messaging is reused, not rebuilt.** The concise beneath-field validation (error icon/text, danger boundary, programmatic association) reuses the TFL-1171 / R22 pattern - `classifyPageRange` / `parsePageRange` (`src/renderer/engine/types.ts`), `validateExportRange` (`src/renderer/components/exportConfig.ts`) and `test/unit/renderer/tfl1116_rangeValidation.test.tsx` (empty vs malformed vs out-of-bounds vs valid, value preserved, `aria-describedby` linked, never color alone, no run on invalid). Do not duplicate the message system; verify against current behaviour first.
7. **Fill vs Edit.** Filling writes values through the existing `fillFormField` path and never flattens. Editing field properties (name, type, tooltip, required/read-only flags, choices, alignment) happens only through APIs that actually exist and must go through the existing undo history; where no API exists the Edit surface shows a truthful read-only property list and the operation is a named **unsupported capability** / separate capability-backed extension, not an invented control. Multi-field `Mixed` is shown where applicable. Type changes and Flatten keep their existing consequence/confirmation flow. Focus moves to the first invalid field only after an explicit validate/complete attempt, never on every keystroke.
8. **Persistence and output.** Values persist through the existing save flows and regenerate appearances via the existing engine path; validate real output by reopening the document in engine tests / supported readers. Ordinary filling changes neither the PDF typeface because UI typography changed nor any PDF page pixel because a view was selected or configured.
9. **Seams reconciled, never duplicated.** Document-conformance validation (PDF/A, PDF/X) stays in the validation/Review flow, separate from field validation. General import intake stays with Drag Drop and Import (TFL-1223) - CSV/FDF/XFDF stay discoverable in the form workflow with their consequence flows, coordinating with, not forking, that intake. The Field Inspector reuses the Selection and Manipulation / "Inspector First" (TFL-1222) and Panels Context Pair primitives. Async save/validate progress, failure and recovery reuse the Feedback and Progress / Activity Shelf (TFL-1216) primitives. Global responsive/accessibility rules come from Responsive and Accessibility / Adaptive Shell (TFL-1224). Flatten / type-change confirmations reuse DialogShell.
10. **Accessibility and adaptation.** Labels, current value, validation, Escape/Close with focus return, resize/theme adaptation, screen-reader names, forced-colors/high-contrast and reduced motion are implemented and keyboard reachable; long/localized labels and 200% scaling hold; Tab/Shift+Tab follows the document's supported field order and canvas/inspector focus link without endlessly cycling.

**Success criteria**

1. **One surface.** Every Forms and Validation entry point (Review dock / Command Palette verbs `forms`, `flatten`, `fillFromCsv`, `exportFormData`, `importFormData`, `validateDocument`; canvas overlay; inspector) routes to the single Guided Fill surface backed by one shared `FormsState`; no parallel store, second reducer or per-call-site CSS override.
2. **The Forms verb is truthful.** Selecting Forms opens the real Guided Fill surface, not Flatten; Flatten keeps its own explicit confirmation flow.
3. **Truthful metadata.** Required state comes only from `/Ff` bit 2; accessible names come from `/TU` or the field name with a truthful fallback; no synthesized label, required flag or email semantics; unsupported constraints (including email) are listed, not rendered.
4. **Fill vs Edit.** Fill writes values and never flattens; Edit is a distinct surface that changes a property only through a real API and undo history, shows `Mixed` where applicable, and classifies any unavailable property edit as unsupported.
5. **Validation.** Concise, programmatically associated validation sits beneath the field with an error icon/text and a danger boundary that explains the correction and never relies on colour alone; empty vs invalid are distinguished (TFL-1171/R22 reuse); focus moves to the first invalid field only after an explicit validate/complete attempt.
6. **Widget fidelity.** Every supported widget type keeps its real export values, option labels, radio grouping, multiselect, appearance stream, field name, read-only flag and document permission; unsupported types show a useful read-only explanation and are never silently converted.
7. **Scope and totals.** The panel distinguishes document and page scope/totals; repeated field names and widgets across multiple pages are handled correctly.
8. **Persistence and pixels.** Values persist through existing save flows and regenerate appearances; reopening in an engine test/reader validates the output; filling or configuring a view never recolors PDF pixels or changes document content, and inline controls never change the PDF typeface.
9. **Keyboard and focus.** Tab/Shift+Tab follows the document's supported field order; canvas and inspector focus link without endlessly cycling; Escape/Close returns focus.
10. **Accessibility and adaptation.** Light/dark/high-contrast (forced-colors), reduced motion, long/localized labels, IME, narrow supported windows and 200% scaling all hold; screen-reader names are real.
11. **Seams.** Conformance validation stays separate from field validation; CSV/FDF/XFDF stay discoverable in the form workflow without forking the Drag Drop and Import intake; the Field Inspector reuses the Panels/Inspector-First chrome; async states reuse the Activity Shelf primitives.
12. **Evidence and flow.** The inventory document, files changed, CONTROL-INDEX sweep, focused test runs (command + counts), full and compact screenshots in every theme plus high contrast and 200%, and the unsupported-capability list are delivered; standard flow CTO -> backend-dev (A, B) -> frontend-dev (C-G) -> focused qa (H) -> adversary diff-pass (I) -> phase-close QA (J) -> ONE local commit via git-agent (K); no push, release or credential change without explicit operator approval.
