**Current state (verified by reading the repo on 2026-10-03).**

1. The badge is rendered by `ActionDock.tsx:899-921`: an absolutely positioned `<span className="action-dock-minus" data-dock-minus={verb.id}>` (16x16) inside each verb `<button className="action-dock-verb">` (rendered at `ActionDock.tsx:867-922`). It is shown only when `data-dock-edit="true"` (the dock root sets that at `ActionDock.tsx:968`; CSS gates display at `styles.css:15855-15857`).
2. The badge geometry is `position: absolute; top: -5px; right: -5px` (`styles.css:15838-15853`), i.e. it deliberately overhangs its verb box by 5px on the top and right. The verb is `position: relative` (`styles.css:15958-15959`) with no clipping, so the overhang is only safe while every ancestor also refuses to clip it.
3. The verb row is a flex group (`.action-dock-group`, `styles.css:15915-15933`) with no `overflow` set, inside the scroll strip `.action-dock-scroll` (`styles.css:16213-16235`). In its default form the strip is `display: contents` (no box, no clipping); **in the arrows lane it becomes a real scroll box with `overflow-x: auto` (`styles.css:16232`)**. Per CSS overflow rules an `overflow-x: auto` box with the other axis left `visible` computes `overflow-y` to `auto`, so in the arrows lane the strip clips the badge's `-5px` top overhang — a clipping ancestor the badge's geometry did not account for.
4. The dock root `.action-dock` (`styles.css:15693-15745`) is `position: absolute; bottom: 12px; left: 50%` with `padding: 6px 8px`, a measured `max-width` cap and **no `overflow` set**, so the root itself does not clip — but the rightmost badge's `right: -5px` overhang sits on only 8px of dock padding and the whole dock sits near the window's bottom/right edges at small window sizes, so the badge can still resolve past the visible window edge.
5. The containment contract for the dock's own trailing pen already exists and is proven: `phase58_dock_edit.spec.cjs:59-79` (`penContainment`) measures a control's rect against the dock rect, and `def341_dockContainment.test.ts` pins the row-containment rule in `src/renderer/state/dockFit.ts:270-283`. The minus badge was never given the same containment guarantee.

**CTO RULINGS:**

1. **Scope and files.** Renderer only. Modified: `src/renderer/components/ActionDock.tsx` and `src/renderer/styles.css` (the dock edit block `15836-15933` and, if needed, the scroll-strip block `16202-16254`). New: `test/unit/renderer/phase95_dockMinusContainment.test.ts` and `e2e/phase95_dock_edit_overflow.spec.cjs`. Do NOT touch any icon glyph, size or stroke (Phase 94 owns icon identity), any dock verb behaviour, the pen, the plus, the picker, the context menu, or any other component. No `src/main/`, `src/shared/`, no `package.json` change, no new dependency.
2. **The badge is wholly inside its visible container, always.** In edit mode every rendered `[data-dock-minus]` must be fully inside the dock's bounding box AND fully inside the window viewport, at the minimum supported window size, a typical size and the maximum interface zoom/scale. "Fully inside" means every badge edge is within the containing box's edges (allowing the existing 0.5px sub-pixel tolerance used by `penContainment`). Prefer a fix that removes the overhang structurally (reserve badge space so the badge sits inside the verb/dock box) over widening a clipping ancestor, so the invariant holds at any future dock layout; the `-5px` offsets are the prime suspect.
3. **No clipping ancestor may cover the badge.** In the arrows lane the scroll strip must not clip the badge's top edge. Either give the badge geometry that survives the strip's computed `overflow-y: auto`, or give the strip the vertical headroom the badge needs. The fix must be proven in the arrows lane as well as the labelled/idle rungs.
4. **Fully clickable, not merely painted.** A click on the badge's centre (and on each badge's visible area) must invoke `removeTool` for that verb and must NOT run the verb (`ActionDock.tsx:906-917`). No badge may be covered by another element at its hit point.
5. **Widespread sweep, bounded.** Sweep the dock and its adjacent dense control surfaces for the same class of defect: a control that paints or hit-tests outside its visible container or the window at any supported width/scale. Named surfaces: the dock verb row and its arrows lane, the dock pen and plus controls, the canvas pills (`.canvas-pill`), the stage rail, the tab strip, and the inspector/panel headers. The developer returns a verdict (**isolated** or **systemic**) with `file:line` anchors for every additional occurrence; every additional occurrence is either fixed in this phase or filed as a named DEF entry by qa with evidence. The sweep is bounded to these surfaces — do not broaden into an app-wide audit.
6. **Durable recurrence guard.** The phase ships `test/unit/renderer/phase95_dockMinusContainment.test.ts` (a source/CSS contract that fails if the minus badge is positioned so it can escape its verb box — e.g. it pins non-negative insets and/or the reserved-space rule that replaces the overhang) AND `e2e/phase95_dock_edit_overflow.spec.cjs` (the runtime oracle that measures every `[data-dock-minus]` against the dock box and the viewport at three widths/scales). The e2e must be demonstrated to FAIL against the pre-fix build and PASS after it. Name the guard's location and how it fails in the report.
7. **No regression, fail-loud parity.** Dock behaviour, edit-mode entry/exit, the jiggle, tool removal, pin/unpin, the arrows lane, the idle state and the existing dock suites keep their shipped behaviour. No control becomes a no-op. Main process, engine, save/export, and settings are untouched.
8. **CONTROL-INDEX.** This phase adds **no new app action and no new window**. The controls it exercises are the EXISTING dock edit controls: the dock pen `[data-dock-edit-toggle]` (arms/disarms edit mode), each verb's minus `[data-dock-minus]` (removes that verb without running it), the plus `[data-dock-plus]` (opens the picker), and the dock verbs themselves. The Phase 95 e2e proves each still performs its shipped action (no-op sweep) AND that every minus badge is fully inside the dock box and the viewport at the three width/scale points.
9. **Settings impact:** none. No new persisted `AppSettings` field, no change to any existing settings shape, no new settings channel and no credential. Renderer-only, offline layout-correctness fix; it adds no IPC and no main-process code. No network call is added.
